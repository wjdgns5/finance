# 포트폴리오용 기술 설명·시연

현재 구현0.6.0과 직접 실행한 검증만 설명합니다. 공개 배포·실시간 가격·사용자 인증·성능 향상 수치를 주장하지 않습니다. 기존 Stock Insight 소스는 제공되지 않아 별도 기반으로 구성했으며 기존 서비스 대비 회귀·성능 비교 자료는 없습니다.

## 30초 설명 예시

“기업명이나 종목코드로 연간 재무와 투자지표를 조회하는 Spring Boot·React 앱입니다. DART 응답을 표준 계정으로 정규화하고 원본 접수번호와 기간을 보존했습니다. 금융 계산은 BigDecimal로 처리하고, 우선주나 보통주 EPS 근거가 부족하면 N/A와 이유를 보여줍니다. Mock·실데이터 모드를 분리하고 MySQL 통합과 실제 브라우저의 오류·복구까지 검증했습니다.”

이 문장을 외우기보다 아래 시연을 직접 재현한 뒤 본인의 표현으로 설명하세요. 금융 공식과 판단 조건은 [정책5.3](../stock-insight-backend/docs/financial-policy.md#53-지표-기준표)을 기준으로 답합니다.

## 2분 기술 설명 순서

1. **문제:** 다양한 계정과 결측을 단순 숫자 표로 옮기면 서로 다른 범위나 확인되지 않은 수치를 비교하기 쉽습니다.
2. **데이터 처리:** DART Client→전용 DTO→정규화→Entity 저장→응답 DTO로 분리하고 원본·메타를 추적합니다.
3. **정확성:** BigDecimal과 DECIMAL·JSON 문자열을 사용합니다. 공식은 백엔드 한 곳에서 계산하며 N/A를0으로 바꾸지 않습니다.
4. **사용성:** 요약→4탭→툴팁·표로 설명 깊이를 나눕니다. 차트에서 연결/별도와 결측 구간을 섞지 않습니다.
5. **검증과 한계:** 백엔드217개·프론트엔드21개, 패키지HTTP17개·브라우저15개 시나리오를 확인했습니다. 사용자의 공시 원문 대조는 아직 미확인입니다.

## 근거로 설명할 문제 해결

### 같은 당기순이익이 두 표에 나타나는 사례

실제 DART 응답에서 IS와 CIS에 같은 당기순이익이 나타났습니다. 모든 중복을 임의로 합치지 않고 ID·이름·상세·원금액이 같은 한 쌍일 때만 IS를 선택했습니다. 같은 표 안의 중복이나 충돌 값은 모호한 계정으로 유지합니다. 두 원본은 JSON에 남깁니다.

코드: [DartNormalizer](../stock-insight-backend/src/main/java/com/stockinsight/provider/dart/DartNormalizer.java). 근거: [실제 응답 테스트](../stock-insight-backend/src/test/java/com/stockinsight/provider/LiveDartSamplesTest.java).

### 첫 수집 때 기업 개요와 계산값이 다른 시점인 사례

재무 수집이 우선주 여부를 갱신하기 전에 기업 기본정보가 먼저 도착해 화면에 미확인 상태가 남았습니다. 재무·지표·이력은 병렬로 읽되 기업 기본정보는 재무 준비 이후에 읽도록 바꿨습니다. 요청 순서 테스트와 신규 실제 기업 조회로 확인했습니다.

코드: [loadDashboard](../stock-insight-frontend/src/lib/api.ts). 근거: [API 회귀 테스트](../stock-insight-frontend/src/lib/api.test.ts).

### 느린 기업 응답이 마지막 선택을 덮어쓸 수 있는 사례

기업 전환 시 이전 요청을 취소하고 완료 후에도 취소 여부를 확인합니다. 응답의 기업·모드·연도·기준·공시 정보를 검사합니다. QA 프록시에서 첫 기업을2.5초 지연시키고 다른 기업을 선택한 뒤 최종 수치가 유지되는지 확인했습니다.

코드: [DashboardApp](../stock-insight-frontend/src/DashboardApp.tsx). 근거: [브라우저 기록](../stock-insight-frontend/docs/phase-6-browser-verification.json).

### CORS와 실제 요청 실행의 경계를 구분한 사례

외부 Origin의 단순 POST가 로컬 수집 API까지 도달하는 것을 테스트로 재현했습니다. Host·Origin·cross-site 검사를 추가하고, 로컬 CLI·프록시 요청과 내부 예외 비노출을 함께 검사했습니다. 이 요청 경계가 로그인·사용자 인증을 구현한 것은 아닙니다.

코드: [LocalApiPolicy](../stock-insight-backend/src/main/java/com/stockinsight/api/LocalApiPolicy.java). 근거: [보안 테스트](../stock-insight-backend/src/test/java/com/stockinsight/api/LocalApiPolicyTest.java).

실제 외부 API를 사용할 수 없으면 Mock·QA 시연과 이미 저장한 실제 응답 검증을 구분해 보여줍니다. API 키가 포함된 설정 파일은 시연 자료에 넣지 않습니다.

## 면접 질문과 답변 요점

1. **지표를 왜 DB에 저장하지 않았나요?** 저장 계정이 갱신되면 요청 시 같은 기준으로 계산합니다. 별도 지표 테이블 동기화 비용을 줄였고 요청당 계산 비용은 한계입니다.
2. **N/A를0으로 채우면 안 되나요?** 실제0과 근거 부족은 의미가 다릅니다. 값·status·reasonCode·reason을 함께 전달합니다.
3. **정규화 실패는 어떻게 추적하나요?** 원본 JSON·계정 식별정보·공시 접수번호·기간·경고를 보존해 잘못 선택했는지 되짚습니다.
4. **왜 외부 요청 중 DB 쓰기 트랜잭션을 유지하지 않나요?** 네트워크 대기와 DB 갱신의 책임을 분리하고, 정상 저장과 실패 이력을 짧은 트랜잭션으로 처리합니다.
5. **TypeScript면 API 검사가 충분하지 않나요?** 빌드 시 타입은 실제 JSON을 검증하지 않으므로 구조·금액 문자열·메타를 실행 시 확인합니다.
6. **자동 검증과 사용자 대조의 차이는?** 샘플 정규화·계산·저장·화면 검증과, 사람이 공시 원문·주석을 읽고 대조하는 확인은 별개입니다.

## 다음 개선을 설명할 때

현재 로컬 사용 범위의 한계에서 출발합니다. 동시 수집 병목을 측정한 뒤 기업별 잠금·작업 큐를 검토하고, 사용자의 공시 대조와 오류 사례를 더 축적할 수 있습니다. 금융 기준을 확장할 때는 기존 결과에 미치는 영향을 먼저 검토합니다. 구현하지 않은 개선을 성과로 적지 않습니다.

직접 해볼 것: 세 문제 해결 사례 중 하나를 골라 코드의 조건문과 테스트 기대값을 짚으면서2분 안에 설명하세요. 힌트는 ‘문제→판정 기준→수정→증거→남은 한계’입니다.

전체 설계 이유는 [결정 기록](design-decisions.md), 정확한 시험 범위는 [검증 안내](verification.md)를 참조하세요.
